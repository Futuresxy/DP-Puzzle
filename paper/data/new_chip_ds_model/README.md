# 真实请求长度加权的芯片配比模型

本目录将三类输入分开：已综合 DP 的面积与活动功耗、公开服务记录的请求长度、DeepSeek-V4.1-Flash 的计算量及精度迁移假设。输出为固定预算下、batch=1 冷启动 prefill 的主要 GEMM 理想计算时间。请求分布属于各自的服务、应用和采样时期。

## 2026-11-18 评估结果

下表按实际输入 token 数计算，五个迁移场景等权。整体加速为相对同预算 `1:2:4` 的平均计算时间之比。首次调用是全部智能体调用的子集，三种样本分别评分。

| 请求分布 | 纳入请求 | 输入中位数 | 综合最优 | 理想 GEMM 加速 | 基线 / 最优平均时间 |
|---|---:|---:|---|---:|---:|
| Azure 对话，2024-05-12 首 6 个 UTC 小时 | 514,840 | 950 | `1:4:8` | 1.127× | 40.55 / 35.97 ms |
| FreeInference，2026-08-30 至 09-05 分区，会话首次调用 | 2,047 | 28,991 | `1:4:8` | 1.137× | 2.255 / 1.983 s |
| 同一分区，全部智能体调用按冷启动重放 | 190,542 | 170,022¹ | `1:4:8` | 1.143× | 5.623 / 4.919 s |
| 原 11 个上下文等权对照 | 11 个长度点 | — | `1:4:8` | 1.163× | 5.124 / 4.406 s |

¹ 中位数按原始 190,544 次调用统计，2 条超过模型的 1,048,576 token 上限。首调用最接近本案例的冷启动设定，后续调用的完整历史在真实服务中可能命中前缀缓存。[请求来源、字段与归属](traces/README.md)

**硬件约束与请求分布各自起什么作用。** `1:4:8` 的 29 个物理 core 在 BF16/MXFP8/MXFP4 模式下分别可开启 29/19/28 个，`1:2:8` 的 32 个 core 在三种模式下均可开启。固定同一条请求分布、将各模式吞吐乘以 `hardware.csv` 中的 `fixed_policy_cores / active_cores` 重算旧模型，三个经验分布的综合最优都回到 `1:2:8`（Azure、首调用、全部调用分别为 1.076×、1.096×、1.104×）。本实验中，是否允许各精度独立选择活跃 core 决定了第一名；将均匀长度替换为样本频率改变了收益幅度。基于两批服务数据的结论仅适用于这里的预算和场景权重。

**具体迁移阶段偏好不同。** 按会话首次调用计，A–E 的最佳配比分别为 `1:4:4`、`1:2:6`、`1:8:16`、`1:8:16`、`1:2:16`，加速比分别为 1.049×、1.052×、1.241×、1.366×、1.791×。一次选定同一颗芯片时，`1:4:8` 在任何单个阶段都不居首，综合平均用时却最短。若目标改为最小化跨阶段最坏损失，首次调用分布选 `1:2:8`（最坏比当场景最优慢 15.61%）；全调用分布也选 `1:2:8`（14.49%），Azure 对话则选 `1:6:12`（17.81%）。

**长度上限影响覆盖率。** Azure 对话样本有 51.03% 短于 1K，最长为 7,999 token。全部智能体调用中 60.66% 超过 128K，31.49% 超过 256K；即使只取会话首次调用，也分别有 22.72% 和 11.43% 超过这两条界限。对完整智能体调用仅保留不超过 128K 或 256K 的请求时，`1:4:8` 仍最优，加速分别为 1.125×、1.130×，全模型支持范围为 1.143×。

**代表长度适于展示分布。** 若将 Azure 对话实际长度替换为 11 个代表点，基线平均计算时间会高估 15.01%，尽管最优配比及其相对加速几乎相同。主报告使用真实长度，分桶近似另报。[11 档请求频率](results/context_weights.csv) · [完整配比评分](results/scores.csv) · [分布与综合加速图](results/comparison.pdf)

## 面积决定部署，运行模式决定活跃核心

以 36 个基线 `1:2:4` compute core 标定面积。每个 compute core 按四个 64-DP Tensor Core 阵列建模，合计 $d=256$ 个 DP。计算频率为 1 GHz，每个 DP 每拍可接受一次独立点积。基线阵列面积占比 $\alpha=0.327$ 是参照 Ascend Cube cluster 面积比例选取的参数。各配比共用同样的单 core 外围存储和控制面积。

设 $A_r$ 为配比 $r$ 的单 DP 综合面积，$A_0$ 为基线值。可部署的物理核心数固定为

$$
N_r=\left\lfloor\frac{36}{1-\alpha+\alpha A_r/A_0}\right\rfloor.
$$

设 $P_{r,p}$ 为该 DP 在精度 $p$ 下的总功耗。取 $B=\beta\,36d\max_p P_{0,p}$，$\beta=1$，得到 **147.4744 W** 的全芯片 DP 阵列功耗预算。每个 GEMM 阶段以单一精度运行，开启的核心数取满足下式的最大整数：

$$
n_{r,p}\le N_r,\qquad d[n_{r,p}P_{r,p}+(N_r-n_{r,p})P_{r,\mathrm{idle}}]\le B.
$$

活跃模式功耗来自 Qwen3-8B 层 0 MLP 输入驱动的门级活动估算，包含动态和静态功耗。空闲 DP 按停止动态翻转处理，闲置漏电取该设计三种已测模式中最大的静态功耗作为近似。所有物理 core 均占面积，并计入其活动或空闲阵列功耗。预算仅覆盖阵列，外围功耗、温度演化、调频和启停延迟均在模型范围之外。算力只对当前执行模式计量，以 $2fdK_{r,p}n_{r,p}$ FLOP/s 表示；精度模式互斥。

## 输入分布与五种迁移

长度采用每次 API 调用的完整输入 token 数。历史对话和工具内容可能已包含在输入里。相同长度在 DeepSeek 配置下做一次冷 prefill 计算，实际服务的缓存命中、排队、输出 token 和 decode 时间均排除。源模型和代理服务可能使用不同 tokenizer，此处迁移 token 数分布。计算阵列按满利用率建模、操作数供应充足。FP32 工作单列于原账本，计时涵盖 H/Q/E 三类 GEMM。

| 阶段 | 在上一阶段基础上的变化 |
|---|---|
| A | 原始映射，routed experts 的 W4A8 使用 FP8 计算能力 |
| B | Routed experts 转为 FP4 计算 |
| C | 主 SWA/CSA QK/PV 和 grouped O-down 从 BF16 转为 FP8 |
| D | Shared experts 和 Q-up/O-up 从 FP8 转为 FP4 |
| E | C 中的主 attention 和 grouped O-down 继续转为 FP4 |

其余算子保留原精度。复用仓库的完整 CED prefill 算子账本和 A–E 映射，每次执行检查 11 个原始长度的 55 组 FLOP 数逐一吻合。五个场景各占 1/5，这是对未来迁移方向的均衡比较。实际请求频率仅用于上下文长度维度。

每种 trace 单独统计。以 $h_L$ 表示输入长度 $L$ 的请求数，$F_{s,L,p}$ 为相应场景及长度的分精度 FLOP 数。各设计整体评分为 $S_r=\bar T_0/\bar T_r$，其中

$$
\bar T_r=\tfrac15\sum_s\sum_L\frac{h_L}{\sum_j h_j}
\sum_p \frac{F_{s,L,p}}{2fdK_{r,p}n_{r,p}}.
$$

`exact` 使用每个实际的正整数长度，包括低于 1024 token 的请求。长度大于配置上限 1,048,576 的请求在 manifest 中计数，并从评分分母中扣除。保留的请求重新归一化。输出的 11 个展示区间以 1024 到 1,048,576 的倍增序列为代表点，以相邻代表点的几何中点分界。最低区间从 1 开始，最高区间截至模型上限。另行输出 `grid`，用于检查将各区间全部请求取为代表长度的误差。原 11 点各赋相同请求数的对照为 `uniform_grid`。最坏场景损失取五个场景中 $T_{r,s}/\min_jT_{j,s}-1$ 的最大值。

## 复现与输出

在 `paper/` 下执行：

```bash
python3 data/new_chip_ds_model/evaluate.py
python3 data/new_chip_ds_model/plot_comparison.py
```

脚本默认读取同目录 `traces/*_histogram.csv`，支持重复指定 `--trace PATH` 和 `--output DIR`。每份输入包含 `input_tokens,requests` 两列。硬件数据入口为 `data/DP_area_power/`，迁移及硬件参数入口为 `data/inputs/v41_five_stage.json`。实测长度较长时按不同长度逐一计算，聚合发生在算子计算量得到之后。

- `results/hardware.csv` 给出物理及活跃 core 数、理想 TFLOP/s、已占面积、活动与空闲功耗代理及阵列总功耗。
- `results/context_weights.csv` 给出每个区间的整数边界、请求数和概率，包括频率为零的区间。
- `results/workload.csv` 给出各区间内按真实频率聚合的每请求 H/Q/E 计算量。
- `results/scores.csv` 给出各样本、方法、配比在 A–E 和 All 的平均时间、加速、排名及相对损失。
- `results/length_cap_sensitivity.csv` 单独报告在 128K 或 256K 截点确实改变请求集合时的条件评分。此处筛选请求并重新归一化，保留请求的完整长度。
- `results/manifest.json` 记录输入指纹、长度覆盖与超界请求数。源模型配置的版本溯源说明见 `data/evidence/v41_five_stage_20261117/manifest.json`。
